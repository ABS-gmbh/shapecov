# Corpus

98 entries, each one XDR value with a manifest record: 95 real ledgers (LedgerCloseMeta) and 3
generated values. The real ledgers come from three sources:

| Source | Entries | `source.kind` |
|---|---|---|
| stellar-core's golden LedgerCloseMeta (`test-lcm-current`, the `--check-lcm` files), byte-identical | 46 | `stellar_core_golden` |
| testnet (19) and pubnet (11) history, from Stellar's public ledger archive | 30 | `network_ledger` |
| a local stellar-core running fixed scenarios (`tools/localcore.py`): 30.0.0, and 22.2.1 for the two protocol 22 scenarios; each regenerates identically on the testnet and mainnet passphrases | 19 | `local_stellar_core` |
| generated from a readable value (`values/`) | 3 | `generated` |

Every entry is checked in CI (RFP check 1) and by `quickcheck.py`; see "How an entry is checked"
below.

| File | What it is |
|---|---|
| `manifest.schema.json` | The manifest format, as JSON Schema (draft 2020-12). |
| `manifest.json` | One record per entry. |
| `entries/*.xdr.b64` | One XDR value per file, one line of base64. |
| `values/*.json` | The readable value each generated entry is encoded from. |
| `evidence/*.md` | Recorded reproductions of sightings and findings. |
| `CAP-COVERAGE.md`, `cap-coverage.json`, `cap-map.json`, `caps.json` | Every live CAP and the corpus evidence for it, or why it has no shape in ledger data; generated by `tools/cap_coverage.py`. |
| `cell-protocols.json` | Each schema cell dated to the stellar-xdr tag that introduced it (`tools/cell_protocols.py`). |
| `patterns.json` | Named shapes the schema cannot express as one union case, such as a muxed ID beyond 2^53. |
| `CENSUS.md`, `census.json` | The largest values seen in a sample of 611 network ledgers (`tools/census.py`). |
| `localcore-reproducible.json` | The hash of each local stellar-core scenario per passphrase, checked in CI by regenerating. |
| `sequences.json` | Named runs of consecutive entries that the replay harness ingests into one database in one run (`replay.py run --sequence`), each with the fix it was built for and whether it is blind. |

## Manifest fields

Each entry record carries what the RFP lists, plus what a consumer needs to check the entry
without trusting us.

| Field | Meaning |
|---|---|
| `id` | Stable entry ID. |
| `xdr_type`, `file`, `sha256`, `size_bytes` | What the bytes are and how to verify you have them. |
| `protocol_version` | The ledger's protocol for a real ledger; the lowest protocol whose XDR can decode a synthetic entry. |
| `caps` | CAPs the entry exercises, each tied to the schema cells that show it. |
| `synthetic` | `false` only when a Stellar network or stellar-core produced the bytes. |
| `source` | One of four forms. A network ledger: network, passphrase, sequence, hash, close time, where it was fetched. A stellar-core golden: the stellar-core commit, golden file, record and test. A local stellar-core ledger: version, image, passphrase, sequence, hash and scenario. A generated entry: the generator and the value file. |
| `shape` | Why this entry is in the corpus, in a sentence or two. |
| `cells`, `cells_new_in_protocol` | Every union case and enum value the entry exercises, and which of them are new since the previous XDR version. Computed, not written by hand. |
| `expected.decoded` | Expected decoded values as path and value pairs. |
| `expected.indexer` | What an indexer must produce, derived from the decoded entry. |
| `expected.sdk` | Checks on what an SDK does with the value after decoding it. |
| `validation` | Recorded results of the checks below. |
| `sightings` | Public bug reports the entry reproduces or relates to, with a pointer to the evidence. |

A cell is a union case (`arm:SignerKey.SIGNER_KEY_TYPE_ED25519_SIGNED_PAYLOAD`) or an enum value
(`enum:OperationType.PAYMENT`) of the XDR schema.

A path is dotted XDR field names with `[i]` for array elements. A union is addressed by its
discriminant's own name and its arm's name, for example `v2.ledgerHeader.header.ledgerSeq` or
`v1.tx.operations[0].body.type`. This is the layout of stellar-core's JSON output, so the same
path can be looked up in what stellar-core prints.

## How an entry is checked

`python3 tools/corpus_check.py --sdks rust,js,python,python-xdr,go,java --core --sdk-checks`, and
`--goldens <stellar-core checkout>` for the golden entries.

1. The manifest validates against the schema.
2. The file matches its hash and size.
3. A strict decoder written from the XDR schema, sharing no code with any SDK, decodes the entry;
   re-encoding gives the same bytes; the cells it finds equal the recorded cells.
4. Every `expected.decoded` value matches.
5. The source record agrees with the bytes: ledger sequence, hash, close time and protocol for a
   real ledger; the value file for a generated one.
6. CAP cells are among the entry's cells. Cells new in protocol 30 are found by comparing the
   v28.0 and v30.0 XDR, and force `protocol_version` to 30.
7. Indexer expectations are recomputed from the decoded entry.
8. rs-stellar-xdr, js-stellar-sdk, py-stellar-base, py-stellar-xdr, go-stellar-sdk and
   java-stellar-sdk each decode and re-encode the entry to identical bytes.
9. stellar-core 30.0.0 decodes the entry, and its own JSON output is compared with
   `expected.decoded`.

With `--goldens`, each golden entry is also compared byte for byte with its record in
stellar-core's `test-lcm-current` files. All checks pass for all 98 entries in CI.

## Adding an entry

The corpus grows as new CAPs ship: a new shape comes in as a ledger from one of the three
sources, through one tool, `tools/corpus_add.py`, which derives every checkable field from the
bytes. These are the steps used for `localcore-planted-auth-5` and `localcore-declared-deploy-6`.

1. **Get the ledger.**
   - A ledger on the network: index a range of Stellar's public archive with
     `tools/mine.py scan <testnet|pubnet> <first> <last> --stride N --cache DIR --index F.jsonl`
     (for example `tools/mine.py scan testnet 5726010 5726030 --stride 1 ...`; a few hundred
     ledgers take seconds), then `corpus_add.py --network-index F.jsonl --cache DIR --min-cells N`.
     Per source, it picks the fewest ledgers that together carry every named pattern found in that
     index, then ledgers that add at least N schema cells no entry has yet; so a ledger can be
     chosen for patterns other sources' entries already carry.
   - A shape the network does not have yet (a new protocol, a rare combination): write a scenario
     in `tools/localcore.py` (a function plus a line in `SCENARIOS` and in the docstring). Record each
     ledger that holds the shape as `run["ledger_<name>"] = core.close()`. Run it with
     `python3 tools/localcore.py --scenario <s> --out DIR`, check in `DIR/run.json` that every step
     was applied, and add the scenario to `SCENARIOS` in `tools/localcore_repro.py`.
   - stellar-core golden files: `corpus_add.py --goldens-index F --goldens-checkout DIR`.
2. **Add it.** `python3 tools/corpus_add.py --local-run DIR` (or the network and golden forms
   above), first with `--dry-run`. This writes `entries/<id>.LedgerCloseMeta.xdr.b64` and the
   manifest record: hash, size, protocol, source, cells, patterns with their paths, CAP tags from
   `cap-map.json` for the cells it is designated for, and expected decoded values. It never
   rewrites an existing entry.
3. **Rewrite the two hand fields.** `corpus_add.py` fills `title` and `shape` with a default made
   from the pattern descriptions; replace both with what the ledger shows and why an indexer could
   get it wrong, naming the upstream issue or commit if there is one.
4. **Validate and record.** Build the SDK runners once (README, "Run it"), then
   `python3 tools/corpus_check.py --sdks rust,js,python,python-xdr,go,java --core --record`
   (Docker; without `--sdks` every check but the SDK round trips runs, and a runner that is not
   built is named and stops the run): the independent decoder, the byte-identical re-encode, the expected values, the
   source record, rs-stellar-xdr and five SDK decoders, and stellar-core's own decode. Every check
   must pass (`CORPUS OK`).
5. **Local ledgers only: pin reproducibility.** Run the scenario on both passphrases
   (`localcore_repro.py run --passphrase testnet|pubnet --out D/<net> --scenario <s>`), record with
   `localcore_repro.py check --run D/testnet --run D/pubnet --update`, then check again without
   `--update` (`REPRODUCIBLE`).
6. **Update what is derived from the corpus.**
   - `python3 tools/cap_coverage.py` rewrites `CAP-COVERAGE.md`; `--check` must pass.
   - `python3 guide/check_guide.py` names any guide row whose Entries column changed.
   - `python3 .github/scripts/check_counts.py` names each sentence that states the entry count.
   - `python3 tools/cell_coverage.py` rewrites `COVERAGE.md` and `coverage.json` when the entry
     brings a new cell; `python3 harness/replay/shapes.py` rewrites the per-shape roll-up when it
     carries a pattern; after editing the guide's Entries columns,
     `python3 guide/export_docs.py --prettier DIR` rewrites the docs page.
   - Replay the new entries (`harness/replay/replay.py run --entries <ids> --refs <commit> ...`)
     and run `replay.py check --oracle`. A failure no known issue explains is a candidate finding.

Finish with `python3 quickcheck.py`: every `FAIL` line names the file to update. CI repeats the
checks of steps 4 and 5, the guide and count checks, and the oracle check on the committed replay
results, on every push.

## Limits

- The entries' `caps` field is written by hand and is empty on 44 entries, most of them
  stellar-core goldens added for the schema cells they reach. Per-CAP coverage
  (`CAP-COVERAGE.md`) does not rely on it: it is computed from each entry's cells and patterns.
- 422 of the 538 reachable cells, those a ledger reader can meet (78.4%), appear in a corpus entry,
  and 422 of the 502 that can occur in a closed ledger (84.1%) (`COVERAGE.md`: a cell is a union arm or
  a member of an enum used as a value, in a type `LedgerCloseMeta` reaches). Each of the other 116
  has a class and a reason in `cell-classes.json`, from stellar-core's source: 36 can never be in a
  closed ledger, 17 belong to protocols before 20, 24 need a network or configuration upgrade, 12
  are failures a local stellar-core scenario can produce, 6 need a contract written to produce
  them, 5 appear only in recorded consensus messages, 1 is impractical, and 15 are not classified
  yet. Whole ledgers are not generated; they come from the three sources above.
- The three generated entries are decode-level values, not the output of applied transactions.
- `expected.indexer` is hand-written for 3 entries. The replay oracle (`tools/oracle.py`) derives
  the expected rows for every ledger instead.
