# Corpus

88 entries, each one XDR value with a manifest record: 85 real ledgers (LedgerCloseMeta) and 3
generated values. The real ledgers come from three sources:

| Source | Entries | `source.kind` |
|---|---|---|
| stellar-core's golden LedgerCloseMeta (`test-lcm-current`, the `--check-lcm` files), byte-identical | 46 | `stellar_core_golden` |
| testnet (19) and pubnet (11) history, from Stellar's public ledger archive | 30 | `network_ledger` |
| a local stellar-core running fixed scenarios (`tools/localcore.py`): 30.0.0, and 22.2.1 for the two protocol 22 scenarios; each regenerates identically on the testnet and mainnet passphrases | 9 | `local_stellar_core` |
| generated from a readable value (`values/`) | 3 | `generated` |

Every entry is checked in CI (RFP check 1) and by `quickcheck.py`; see "How an entry is checked"
below.

| File | What it is |
|---|---|
| `manifest.schema.json` | The manifest format, as JSON Schema (draft 2020-12). |
| `manifest.json` | One record per entry. |
| `entries/*.xdr.b64` | One XDR value per file, one line of base64. |
| `values/*.json` | The readable value each generated entry is encoded from. |
| `evidence/*.md` | Recorded reproductions of sightings and findings. |
| `CAP-COVERAGE.md`, `cap-coverage.json`, `cap-map.json`, `caps.json` | Every live CAP and the corpus evidence for it, or why it has no shape in ledger data; generated by `tools/cap_coverage.py`. |
| `cell-protocols.json` | Each schema cell dated to the stellar-xdr tag that introduced it (`tools/cell_protocols.py`). |
| `patterns.json` | Named shapes the schema cannot express as one union case, such as a muxed ID beyond 2^53. |
| `CENSUS.md`, `census.json` | The largest values seen in a sample of 611 network ledgers (`tools/census.py`). |
| `localcore-reproducible.json` | The hash of each local stellar-core scenario per passphrase, checked in CI by regenerating. |

## Manifest fields

Each entry record carries what the RFP lists, plus what a consumer needs to check the entry
without trusting us.

| Field | Meaning |
|---|---|
| `id` | Stable entry ID. |
| `xdr_type`, `file`, `sha256`, `size_bytes` | What the bytes are and how to verify you have them. |
| `protocol_version` | The ledger's protocol for a real ledger; the lowest protocol whose XDR can decode a synthetic entry. |
| `caps` | CAPs the entry exercises, each tied to the schema cells that show it. |
| `synthetic` | `false` only when a Stellar network or stellar-core produced the bytes. |
| `source` | One of four forms. A network ledger: network, passphrase, sequence, hash, close time, where it was fetched. A stellar-core golden: the stellar-core commit, golden file, record and test. A local stellar-core ledger: version, image, passphrase, sequence, hash and scenario. A generated entry: the generator and the value file. |
| `shape` | Why this entry is in the corpus, in a sentence or two. |
| `cells`, `cells_new_in_protocol` | Every union case and enum value the entry exercises, and which of them are new since the previous XDR version. Computed, not written by hand. |
| `expected.decoded` | Expected decoded values as path and value pairs. |
| `expected.indexer` | What an indexer must produce, derived from the decoded entry. |
| `expected.sdk` | Checks on what an SDK does with the value after decoding it. |
| `validation` | Recorded results of the checks below. |
| `sightings` | Public bug reports the entry reproduces or relates to, with a pointer to the evidence. |

A cell is a union case (`arm:SignerKey.SIGNER_KEY_TYPE_ED25519_SIGNED_PAYLOAD`) or an enum value
(`enum:OperationType.PAYMENT`) of the XDR schema.

A path is dotted XDR field names with `[i]` for array elements. A union is addressed by its
discriminant's own name and its arm's name, for example `v2.ledgerHeader.header.ledgerSeq` or
`v1.tx.operations[0].body.type`. This is the layout of stellar-core's JSON output, so the same
path can be looked up in what stellar-core prints.

## How an entry is checked

`python3 tools/corpus_check.py --sdks rust,js,python,python-xdr,go,java --core --sdk-checks`, and
`--goldens <stellar-core checkout>` for the golden entries.

1. The manifest validates against the schema.
2. The file matches its hash and size.
3. A strict decoder written from the XDR schema, sharing no code with any SDK, decodes the entry;
   re-encoding gives the same bytes; the cells it finds equal the recorded cells.
4. Every `expected.decoded` value matches.
5. The source record agrees with the bytes: ledger sequence, hash, close time and protocol for a
   real ledger; the value file for a generated one.
6. CAP cells are among the entry's cells. Cells new in protocol 30 are found by comparing the
   v28.0 and v30.0 XDR, and force `protocol_version` to 30.
7. Indexer expectations are recomputed from the decoded entry.
8. rs-stellar-xdr, js-stellar-sdk, py-stellar-base, py-stellar-xdr, go-stellar-sdk and
   java-stellar-sdk each decode and re-encode the entry to identical bytes.
9. stellar-core 30.0.0 decodes the entry, and its own JSON output is compared with
   `expected.decoded`.

With `--goldens`, each golden entry is also compared byte for byte with its record in
stellar-core's `test-lcm-current` files. All checks pass for all 88 entries in CI.

## Limits

- The entries' `caps` field is written by hand and is empty on 44 entries, most of them
  stellar-core goldens added for the schema cells they reach. Per-CAP coverage
  (`CAP-COVERAGE.md`) does not rely on it: it is computed from each entry's cells and patterns.
- 352 of the 1,188 schema cells appear in a corpus entry. Whole ledgers are not generated; they
  come from the three sources above.
- The three generated entries are decode-level values, not the output of applied transactions.
- `expected.indexer` is hand-written for 3 entries. The replay oracle (`tools/oracle.py`) derives
  the expected rows for every ledger instead.
