Every shape named here has a **corpus pattern** (for example `memo-text-not-utf8`), defined in [`corpus/patterns.json`](https://github.com/ABS-gmbh/shapecov/blob/main/corpus/patterns.json). Where the corpus has real ledgers that contain the shape, the tables give the count, so you can replay them through your own pipeline with the [replay harness](https://github.com/ABS-gmbh/shapecov/blob/main/harness/replay/README.md). [`check_guide.py`](https://github.com/ABS-gmbh/shapecov/blob/main/guide/check_guide.py) keeps the tables in step with the corpus manifest (see [Appendix](#appendix-how-this-guide-is-checked)).

The one rule behind everything below: **valid is not the same as well-formed for your database.** stellar-core accepts a transaction if it follows the protocol. The protocol allows memo text that is not UTF-8, 64-bit IDs that no float can hold, signer keys 100 bytes long, and contract values nested deeper than most recursive code expects. The corpus holds ledgers with all of these: network ledgers for most, and a ledger closed by a local stellar-core 30.0.0 for the memo text (`localcore-memo-and-offer-p30-4`). In that ledger the memo's bytes also appear, unchanged, in the payment's transfer event.

## 1. What stellar-core validates, field by field

stellar-core decodes every transaction strictly: lengths must not exceed their XDR maximum and padding must be zero. Beyond that, it checks only what the protocol needs. **We found no UTF-8 check on any string field, in stellar-core or in the Soroban host.** Two fields are stricter and are limited to printable ASCII: the `ManageData` name and the home domain.

"Checked" below means the transaction is rejected, or the operation fails, if the check fails. Bracketed numbers point to the [sources](#sources) at the end of this section.

### The transaction itself: signatures, sequence numbers, fees, time bounds

These are the fields stellar-core does validate. It checks them when a node accepts a transaction, and again when the transaction is applied: against the close time and sequence number of the ledger being closed, and against the state the earlier transactions of the same ledger left [20]. So a transaction in a closed ledger has not necessarily passed them. An earlier transaction in the same ledger can change the source's sequence number or signers, and the later one is then in the ledger with `txBAD_SEQ`, `txBAD_AUTH`, `txBAD_AUTH_EXTRA` or `txBAD_MIN_SEQ_AGE_OR_GAP`, or with `txFAILED` and `opBAD_AUTH` on one operation. A transaction that begins a sponsorship and does not end it is in the ledger with `txBAD_SPONSORSHIP` (Corpus: `tx-bad-sponsorship-at-apply`) [20]. **Read validity from the result code, never from inclusion.** The fee is charged either way, before any transaction of the ledger is applied [22]. The corpus has each of these: ledgers from a local stellar-core in which an earlier transaction, signed by the victim's account, bumped its sequence number or changed its signers (`localcore-tx-failures-plain-12`, `localcore-tx-failures-bumped-13`, the second inside fee bumps, and `localcore-op-failures-8`), and three of stellar-core's own golden ledgers.

### What stellar-core itself does with each row

The tables above cite stellar-core's source for every claim. For most rows, stellar-core's own answer is also on record: a probe, or a ledger that stellar-core closed. A probe is a transaction built to break the rule, or to sit just inside it, and submitted to stellar-core. A ledger in the corpus shows that stellar-core accepted that shape. Where neither exists, the row says it rests on the citation alone, and why.

**19 of 29 rows** have a verdict from stellar-core itself on every side they make a claim about, **8** on one side, and **2** rest on the source citations alone. Rows with a side that has only a citation: Signatures; Time bounds and other preconditions; Memo ID, hash, return; Muxed account (source, destination, fee source); Asset code; Nesting of contract values (`ScVal`); Contract strings (`ScString`); Integers; Authorization entries; Addresses in contract values.

A probe is a transaction built to break, or to sit just inside, the rule: 50 probes, plus 1 setup transaction that deploys the native asset contract they call (`guide/probes.json` holds all 51 records). `guide/probe_core.py` submits them to a local stellar-core 30.0.0 at protocol 30, and CI runs it on every change. "Core closed ledgers with" names corpus patterns found in ledgers stellar-core closed, so core accepted that shape.

## 2. Depth and size caps

Recursive structures in the ledger are bounded by the network, but not always by numbers your code can rely on without thought. Use these bounds to pick caps that never reject valid data:

| Structure | Bound the network enforces | Recommended cap | Largest seen in the sample: pubnet / testnet |
| --- | --- | --- | --- |
| Contract values in storage, events and return values | At most 100 levels: the host refuses to convert anything deeper [12] | Walk with a depth counter and stop at 100. _(Inference: every such value passed through the host's conversion, so a cap of 100 should never reject one.)_ | 7 / 11 levels (all contract values, nesting of vectors and maps) |
| Contract values in transaction arguments | Only the envelope's XDR depth of 1000 (from protocol 28) when the transaction failed before the host read them [12] | Walk with a depth counter. Past your cap, truncate and record that you did; do not reject the ledger. | counted in the row above |
| Soroban authorization trees | No limit of their own; only XDR depth and transaction size [15] | Iterate with an explicit stack and a depth counter, truncating as above. | 4 / 3 levels (root = 1) |
| Whole envelopes and `LedgerCloseMeta` | stellar-core parses envelopes with rs-stellar-xdr at depth 1000 (from protocol 28) | Set your decoder's depth limit explicitly. Rust's `Limits::none()` is unbounded; Go's default is 1500. Depth is counted per XDR type, not per contract-value level, and libraries count differently, so test your limit on the corpus's deepest entries. | not measured |
| Claim predicates | 4 levels [8] | 4 is safe. | not measured |
| Path payment path, operations, signatures, `extraSigners`, claimants, memo text | 5, 100, 20, 2, 10, 28 bytes (XDR) | The XDR maxima are exact. Size buffers to them, and test at the maximum (`operations-at-max-100`, `signatures-at-max-20`). | operations 100 / 76; signatures 20 / 13; memo text 28 / 28 bytes; the others not measured |
| Contract value lengths | Symbols: 32 bytes (XDR) [13]. Vectors, maps, strings and bytes have no XDR maximum, only the size settings in the next row | Size buffers from the network settings, not from what you have seen. | vector 100 / 255 elements; map 13 / 50 entries; string 258 / 84 bytes; symbol 32 / 32 bytes; bytes 1,568 / 26,889 |
| Event bytes per transaction, contract data entry size, key size, transaction size | Network configuration settings (`ConfigSettingContractEventsV0`, `CONTRACT_DATA_ENTRY_SIZE_BYTES`, `CONTRACT_DATA_KEY_SIZE_BYTES`, `ConfigSettingContractBandwidthV0.txMaxSizeBytes`), changed by network upgrades | Read them from the ledger's `ConfigSetting` entries; do not hard-code them. | not measured |
| Number of contract events per transaction | No limit found other than the total event bytes | Do not assume a small count. | not measured |

"Largest seen in the sample" is the largest value in every 20,000th ledger of pubnet (from protocol 23) and of testnet: 611 ledgers holding 100,676 transactions. It is an observation of that sample, never a network-wide maximum, and the protocol allows more; where the seen value is far below the bound, a cap set from the sample would reject valid data the sample missed. Ledgers, transactions and the method are in [`corpus/CENSUS.md`](https://github.com/ABS-gmbh/shapecov/blob/main/corpus/CENSUS.md).

A cap protects your process. When one is hit, the safe response is to store what you have, flag the record and keep ingesting. Rejecting the ledger stops your indexer on valid data. That is how stellar/wallet-backend#729 stopped ingestion: one valid signer it could not store stopped every later ledger.

## 3. Participants come from the meta, not the envelope

A transaction's **envelope** records what its submitter asked for. Its **meta** records what stellar-core actually did. The two differ in ways that matter to anyone answering "which accounts did this transaction affect?":

- **Failed transactions are in the ledger.** The fee is charged and the envelope is stored, but no operation took effect. A payment's destination in a failed transaction received nothing. (Corpus: `failed-transaction`, `failed-soroban-transaction`.)
- **Contract calls change accounts that no operation names.** A Stellar Asset Contract call can create a trustline or an account with no `ChangeTrust` or `CreateAccount` operation (CAP-73). Only the meta shows it. Before its fix (#734), stellar/wallet-backend recorded no trustline history for such a trustline (#731; reproduced by the replay harness with `localcore-sac-trust-p28-5`). (Corpus: `soroban-created-trustline`, `soroban-created-account`.)
- **The Soroban authorization tree is a claim.** The host checks the signature and consumes the nonce only for entries a `require_auth` call matched. We found no code that rejects the rest (section 1, [15]). An address in an authorization entry proves nothing on its own. A consumed nonce in the ledger changes (a temporary contract-data entry keyed `LedgerKeyNonce`) shows the entry was used. (Corpus: `auth-nested-invocations`, `auth-tree-4-deep`.)

So derive participants from:

| Source | Gives you | When |
| --- | --- | --- |
| The transaction source and fee source | the accounts that signed and paid | always, even for a failed transaction: stellar-core checks their signatures and charges the fee |
| `LedgerEntryChanges` in the transaction and operation meta | every account, trustline, offer, data entry, claimable balance and contract data entry that was created, updated or removed | successful transactions; fee changes for all |
| Contract events in the meta | token movements (`transfer`, `mint`, `burn`, `clawback`) and their addresses | successful transactions |
| Authorization entries | address-credential entries whose nonce entry the meta shows being created; source-account entries are the transaction source, already counted | successful transactions |

**What goes wrong otherwise.** stellar/wallet-backend took Soroban participants from the declared authorization tree until commit `9538b3ca` ("derive Soroban participants from executed meta, not the auth tree"). It still records envelope-derived operation participants for failed transactions (introduced by #474). In a failed transaction, that lets any submitter put any account into another account's history at the cost of one fee. The [linter](https://github.com/ABS-gmbh/shapecov/blob/main/linter/README.md) rule **SC003** reports this pattern in Go code.

## 4. Muxed and signed-payload addresses

### The strkey forms (SEP-23)

A strkey is a version byte, a payload, and a two-byte CRC16-XModem checksum (little-endian), encoded as unpadded base32. The payload length depends on the version byte:

| Prefix | Kind | Version byte | Payload |
| --- | --- | --- | --- |
| `G` | account | `6 << 3` | 32-byte ed25519 key |
| `M` | muxed account | `12 << 3` | 32-byte ed25519 key, then 8-byte ID (big-endian) |
| `P` | signed payload | `15 << 3` | 32-byte ed25519 key, 4-byte payload length (big-endian), payload of 1 to 64 bytes, zero padding to a multiple of 4: **40 to 100 bytes** |
| `C` | contract | `2 << 3` | 32-byte contract ID |
| `T` | pre-authorized transaction | `19 << 3` | 32-byte hash |
| `X` | hash(x) | `23 << 3` | 32-byte hash |
| `L` | liquidity pool | `11 << 3` | 32-byte pool ID |
| `B` | claimable balance | `1 << 3` | 1 type byte, then 32-byte balance ID |

Two traps in that table:

- **A muxed account's byte order differs between XDR and strkey.** In XDR, `MuxedAccount.med25519` is `{ uint64 id; uint256 ed25519; }`, ID first. In an `M...` strkey, the key comes first and the ID last. Code that copies XDR bytes into a strkey payload produces a valid-looking address for the wrong account.
- **Not every address is 32 bytes.** `M` is 40 and `P` is 40 to 100. A column, buffer or type that holds "version byte + 32 bytes" silently truncates the rest.

### What happened in wallet-backend

The [replay harness](https://github.com/ABS-gmbh/shapecov/blob/main/harness/replay/RESULTS.md) reproduces both of these from one real testnet ledger (`testnet-4437357-signed-payload-signer`, a `SetOptions` that adds a `P...` signer):

| wallet-backend commit | What the indexer did with the `P...` signer |
| --- | --- |
| `79ea2acd` | Stored 33 of its 41 bytes with no error. The stored value reads back as `PBCK2RYY…NSBYVM`, which is not a valid address (stellar/wallet-backend#716). |
| `6e5a5910`, `2a0a84ea` | A length guard turned that into an insert error. The ledger never committed, the cursor never advanced, and ingestion stopped (stellar/wallet-backend#729). |
| `2c873353` and later | Stores the full key in a variable-length column. |

The same happened with muxed addresses. The harness replays a contract call that runs as a muxed account (`localcore-muxed-source-p22-3`):

| wallet-backend commit | What the indexer did with the muxed source |
| --- | --- |
| `79ea2acd` | Recorded the account twice as a participant: as `G...`, and as an `M...` truncated to 33 of its 41 bytes that no longer decodes (#716). |
| `6e5a5910` (#693) to `f8e5786d` | Encoded both strings to the same base-account key. The insert failed on a duplicate primary key and ingestion stopped at the ledger. |
| `bb0b162b` and later | Records the base account once. |

The second row is the lesson: normalising addresses at the storage layer, after the set of participants is built, turns one silent bug into a stopped indexer. Normalise when you derive the participant, not when you write it.

### How to handle them

- **Store the full payload.** Keep the version byte and all payload bytes in a variable-length column, or store muxed accounts as two columns: the base `G...` account and the ID.
- **Decide what a muxed account means for each table.** Balances, signers and account state belong to the base account: reduce `M...` to `G...` (`MuxedAccount.ToAccountId()` in Go) there. Payment history, deposits and anything a customer ID routes should keep the ID. Never let one column hold both forms.
- **Hold 64-bit IDs as unsigned 64-bit integers or decimal strings.** Muxed IDs, memo IDs and offer IDs use the full `uint64` range. 2^64-1 overflows a signed `BIGINT`; anything above 2^53 changes value in a JavaScript `number` or a `float64`. (Corpus: `muxed-id-max`, `muxed-id-beyond-f64`, `muxed-id-zero`, `scaddress-muxed-id-beyond-f64`, `offer-id-beyond-f64`.)
- **Treat ID 0 as an ID.** `M...` with ID 0 is a different address from the plain `G...`. Truthiness checks (`if id:`) treat it as absent.
- **Validate on read, not only on write.** When you read an address back from storage, check that its payload length matches its version byte. `harness/replay/strkeyx.py` has a reference check (`payload_problem`) written from SEP-23.
- **Expect muxed addresses inside contract data.** Since CAP-67, an `ScAddress` can hold a muxed account, and since protocol 30 a muxed contract address. Code that expects only `G...` and `C...` from contract values fails on them. (Corpus: `scaddress-muxed-account`, `scaddress-muxed-contract`.)

## 5. Checklist

Use this when you review an indexer, in any language. The **Linter** column names the [shapecov-lint](https://github.com/ABS-gmbh/shapecov/blob/main/linter/README.md) rule that finds the mistake in Go code. **Replay** marks items that the [replay harness](https://github.com/ABS-gmbh/shapecov/blob/main/harness/replay/README.md) can show against your running indexer once the corpus has an entry with that shape and expectations for it.

| # | Check | Section | Linter | Replay |
| --- | --- | --- | --- | --- |
| 1 | Memo text and contract strings are stored as bytes, or checked for UTF-8 and NUL before they reach a text column. | 1 | SC001 | yes |
| 2 | Muxed IDs, memo IDs and offer IDs are held as unsigned 64-bit integers or decimal strings, never as floats or signed 64-bit. | 4 | SC001 | yes |
| 3 | Addresses are stored with their full payload (40 bytes for `M`, up to 100 for `P`) and checked against their version byte when read back. | 4 | — | yes |
| 4 | Each table states whether it holds the base `G...` account or the muxed form, and never mixes them. | 4 | SC001 | yes |
| 5 | Every recursive walk over contract values or authorization trees has a depth counter and a cap, and truncates instead of failing. | 2 | SC002 | — |
| 6 | The XDR decoder's depth limit is set explicitly, not left at an unbounded or untested default. | 2 | — | — |
| 7 | Size limits come from the ledger's network configuration, not constants. | 2 | — | — |
| 8 | Participants come from the meta. A failed transaction contributes only its source and fee source. | 3 | SC003 | yes |
| 9 | Authorization entries count only when the meta shows their nonce consumed. | 1, 3 | SC001, SC003 | yes |
| 10 | Trustlines and accounts are tracked from ledger changes, so contract-created ones appear. | 3 | — | yes |
| 11 | Liquidity-pool asset pairs are ordered by XDR bytes, not by strkey text. | 1 | — | yes |
| 12 | Contract maps are not converted to text-keyed objects, which merges colliding keys and reorders mixed types. | 1 | — | yes |
| 13 | A value the indexer cannot store is flagged and skipped, and ingestion continues; one valid ledger never stops the indexer. | 2 | — | yes |
| 14 | Ledgers older than protocol 25 are handled: contract invocations there can have a muxed source and a memo. | 1 | — | yes |
| 15 | Whether a transaction took effect comes from its result code. Inclusion in a ledger proves neither signatures nor a valid sequence number: stellar-core checks both again when it applies the transaction. | 1 | — | yes |
| 16 | Fees are read from `feeCharged` in the result, and recorded for failed transactions too; the `fee` field is only a maximum. For a fee bump, the fee source pays, not the inner source. | 1 | — | yes |
| 17 | An account's sequence number is taken from its ledger entry, not inferred from the transactions you saw: a failed transaction can consume one, a `txBAD_SEQ` one does not, and `minSeqNum` skips some. | 1 | — | — |
| 18 | Time and ledger bounds are not used as the time a transaction happened; the ledger's close time is. | 1 | — | — |

## Appendix: how this guide is checked

[`check_guide.py`](https://github.com/ABS-gmbh/shapecov/blob/main/guide/check_guide.py) checks this guide against the corpus manifest. It is the RFP's acceptance check for the guide ("the field-by-field table agrees with the corpus manifest"):

```sh
python3 guide/check_guide.py
```

It fails if:

- the guide names a corpus pattern or entry that does not exist;
- a corpus pattern is not mentioned anywhere in the guide;
- in a table with "Corpus shape", "CAP" and "Entries" columns, the CAP column differs from the pattern's CAPs in `corpus/patterns.json`, or the Entries column differs from the number of manifest entries that carry each pattern.

Every shape the guide describes has at least one corpus entry. Three come from a local stellar-core, not from network history (`tools/localcore.py`):

- `soroban-op-muxed-source`: `localcore-muxed-source-p22-3`, closed by stellar-core 22.2.1 at protocol 22. A contract call whose operation runs as the transaction's muxed source succeeded there. Only validators on stellar-core 22.x or older could have closed such a ledger (section 1, [18]), and those run protocol 22 at most, so expect it when backfilling protocols 20 to 22.
- `memo-text-not-utf8` and `offer-id-beyond-f64`: `localcore-memo-and-offer-p30-4`, closed by stellar-core 30.0.0 at protocol 30. Offer IDs come from a sequential counter, so a value above 2^53 appears on the network only in the envelope of a failed transaction, as it does here.

All three passed the same checks as network entries: the independent decoder, all five SDK round trips and stellar-core 30.0.0's own decoder.

The claims in section 1 were read from the source cited there. Where the guide says "we found no code that…", the absence was established by reading and searching that code, not by a statement in it. Those are the claims a reviewer should check first.
