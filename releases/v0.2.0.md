# ShapeCov v0.2.0

**Draft, not tagged.** These notes are reviewed here like any other file; the figures are filled in
from the repository once the corpus is final, and the count check covers them from then on.

v0.1.0 checked SDK decoders end to end and replayed a corpus through wallet-backend and stellar-etl.
v0.2.0 makes the indexer half a test of real software against its own history, and makes every
claim in the repository something a reader can rerun.

## What changed since v0.1.0

**Three indexers, unmodified.** Replays now run wallet-backend, stellar-etl and Horizon, each at a
given commit or release, against its own database, with every ledger judged by an oracle that
derives the expected rows from the ledger itself. Horizon runs through its own `db reingest`, from
the same data lake. A toy indexer of about a hundred lines (`adapters/example/`) shows the adapter
interface and the participant rule by example.

**Sequences.** Some defects show only across ledgers: a trustline removed and re-added within one
ledger, a contract that rebinds itself after it was classified, a balance created in one ledger and
changed in the next. Named sequences of consecutive ledgers are now ingested into one database in
one run, and the indexer's state at the end is checked as well as each ledger.

**Protocol production.** wallet-backend's SEP-41 and Blend indexing runs during replays the way an
operator turns it on, with the commit's own setup command, so the token and pool tables are tested
too. Nothing is injected into the indexer.

**The backtest.** The RFP's acceptance check for the harness, applied to the 2026 bug history of
wallet-backend and stellar-etl: every fix that concerns a ledger shape is replayed at the commit
before it and at the fix, judged by the oracle alone. Each fix is recorded as detected, missed or
out of scope, with the reason, and each detection says whether the ledger was chosen without
knowledge of the fix. `replay.py backtest` checks every row against the recorded results.

**The sweep.** A stride of pubnet and testnet ledgers from Stellar's public archive, replayed
through the indexers with the oracle, so the oracle is tested on ordinary traffic and not only on
rare shapes. Every failure on it maps to an open upstream issue.

**The RFP's sightings.** Each of the RFP's public sightings is reproduced and run in CI, or the
scoreboard (`harness/sightings/README.md`) says why it cannot be. New this release: js-xdr#165 on
the pinned release, with a weekly check of the newest one, and stellar-etl#454 for amounts above
2^53 stroops.

**Cross-SDK matrix.** Each defect class found in one SDK, checked in the others, from runs and
named sources only (`sdk-matrix/MATRIX.md`).

**The linter** runs on wallet-backend and on stellar-etl; every finding outside the accepted lists
fails CI, and the findings it reports on wallet-backend are real defects, each with an open upstream
issue. It ships as a GitHub Action and as release binaries for five platforms.

**The guide.** Every row of the field tables carries stellar-core's own verdict: a probe sent to a
local stellar-core 30.0.0 or a ledger core closed, or a source citation where neither exists, listed
for the reviewer in `guide/REVIEW.md`. Every checklist item names the corpus entries that exercise it
and the upstream fix or issue where an indexer, SDK or exporter got it wrong. A review gate holds the
developers.stellar.org page under a "not reviewed" caution until a stellar-core or platform engineer
signs the review line.

**One check to look at.** CI's `green` job passes only when every other job has, and a release is
refused unless its commit is on `main` and green. `python3 quickcheck.py` reruns the acceptance
checks from a clone with Python alone, on Python 3.9 to 3.14.

- **Backtest misses**, each with its reason in `harness/replay/BACKTEST.md`:

  - stellar-etl #453: the oracle checks fees through token transfers, not the transactions export's
    fee columns, and no corpus ledger has a muxed Soroban fee source.
